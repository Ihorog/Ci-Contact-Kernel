# CI.AUTH.MOMENT/1.0 — пристрій, згода та межа повноважень

Статус: **DRAFT / не розгорнуто**. Єдиний Ci, без нових постійних служб.
Пов'язаний PR: #101. Окремі бізнес-принципали та HOME.CI не змішувати.

## Намір

Коли чинна серверна політика вимагає сильного підтвердження, Ci показує власнику
один зрозумілий намір та просить систему пристрою підтвердити його через WebAuthn/FIDO2.
Android/Windows або сумісний браузер відображає **власний захищений діалог**
(ключ доступу, відбиток, обличчя, PIN або апаратний ключ — що реально доступно).

Не викликати напряму банківські застосунки, не намагатися копіювати/експортувати
їхні сертифікати, приватні ключі, токени чи біометричні дані. Ключ доступу Ci має
власний RP ID: `mcp-http.cimeika.com.ua`, а не RP банку. Пристрій може
запропонувати наявний системний менеджер ключів доступу після окремого
первинного запису ключа **для Ci**.

## Єдина координата авторизації

`intent -> CI.AUTH.GATEWAY -> policy -> CI.AUTH.MOMENT -> platform WebAuthn -> verified assertion -> bounded permission -> Ci action -> independent evidence`

`CI.AUTH.MOMENT` — фіксація конкретної пропозиції повноважень на певний
момент часу, **не** новий самостійний центр контролю.

Поля мінімального контексту:
- `task_id`, `parent_id`, `principal`, `domain`;
- `target`, `operation`, `purpose`, `effect`;
- `requested_scope`, `policy_ref`, `terms_sha256`;
- `client_id`, `resource`, `rp_id`, `origin`;
- `issued_at`, `expires_at` (не довше 300 секунд);
- `moment_sha256` як хеш канонічного JSON цих полів.

Код дескриптора: `connector/ci_auth_moment.py`.
Цей модуль **готує дані та хеш**, не випускає access token,
не заявляє про перевірку особи й нічого не підписує.

## Виклик системного підтвердження

1. CI.AUTH.GATEWAY перевіряє політику, чинний `task_id`, revision,
   target, scope, поточний principal і необхідність кроку.
   Якщо дія вже дозволена в HOME.CI, додатковий запит **не створюється**.
2. Для confirmation-gated дії сервер генерує короткоживучий challenge, зберігає
   точний дескриптор та його `moment_sha256` у **серверному** pending-запиті.
   Зміна дії, умов, одержувача або прав змінює хеш і анулює стару згоду.
3. Користувач бачить природною мовою **що, кому й навіщо дозволяє**.
   Для згоди відкривається стандартний діалог платформи
   `navigator.credentials.get({publicKey})` або відповідний native Credential Manager.
   Наявність пристрою не дає права непомітно підтвердити дію у фоні.
4. Авторитетний сервер перевіряє підпис ключа Ci, challenge, RP ID, origin,
   user verification, термін, credential, блокування replay та exact `moment_sha256`.
   Лише після цього видається одноразовий обмежений grant.
5. Виконання підтверджується **окремими** доказами. Дозвіл ≠ виконання.

## Доказовий запис

Внутрішній журнал повинен містити: час UTC, causal `task_id`, хеш
контракту, `policy_ref`, серверний nonce/event-id, непрямий credential-ref
(без ідентифікаторів пристрою, що відстежують між сервісами), user verification
PASS/FAIL, дозвіл/відмову, межі, строк, revocation та evidence виконання.
Матеріали чутливого домашнього контуру не дублювати в публічний GitHub.
Лог має бути захищений від перезапису та підтримувати відкликання.

## Юридичний статус

WebAuthn доводить факт перевірки **зареєстрованого ключа Ci** й може бути частиною
доказів згоди з конкретною дією, але сам по собі **не прирівнюється** до
кваліфікованого електронного підпису (КЕП). Для договору або іншої дії,
що юридично вимагає КЕП/Дія.Підпис/визнаного провайдера, потрібно
**окреме провайдерське підтвердження**, його оригінальний документ,
сертифікат, перевірка підпису та незалежна правова кваліфікація.
Не називати WebAuthn підписом договору; не переносити банківські посвідчення
до Ci.

## Фактичний стан і блокери

- Код WebAuthn у PR #101 та модуль контракту — **draft**, не production.
- Passkey власника для Ci не зареєстровано і end-to-end твердження відсутнє.
- Дескриптор `CI.AUTH.MOMENT` ще **не підключений** до серверного challenge.
- Релізний маршрут, сумісність із локальними патчами Orange,
  ChatGPT MCP OAuth і право користування повним MCP у поточному акаунті
  потребують окремої живої верифікації.
- Cihub допускається як **тимчасовий діагностичний канал**, не частина Ci.

## Мінімальне приймання

1. Зареєструвати один passkey **для Ci** після перевіреної локальної
   ініціалізації власником; жодні ключі з банків не імпортувати.
2. Перевірити серверний hash binding і WebAuthn assertion під час реального
   user-verification, включно з відмовою та зміненим `scope` або `target`.
3. Упевнитися, що статус `AUTHORIZED` створено без side effects
   і не виникає повторний consent/grant для того ж causal task.
4. Виконати одну безпечну локальну read-операцію та незалежну перевірку.
5. Лише після цього назвати прямий Ci MCP `VERIFIED`.
